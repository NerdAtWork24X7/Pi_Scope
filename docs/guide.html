Prerequisites

Pi Scope is two pieces: a server + dashboard you open, and a pi extension that feeds it agent telemetry. Here is exactly what each path needs.

PathWhat you needInstall anything?
Linux desktop (AppImage)A Linux desktop, x86_64No — Node 24 is bundled inside
WindowsWindows 10/11 + Node.js 24+Yes — the one-liner below
From source (developers)Node.js 24+Yes — the one-liner below
Feed it agent dataThe pi coding agent — bundledNo — Pi Scope ships its own pi
Any other toolAnything that can POST /eventsA ~10 line script

Node 24+ is the only real requirement — Pi Scope uses node:sqlite, which ships inside Node 24, so there are zero native build steps in the default path. Linux, macOS and Windows all run the same server, dashboard and desktop window; Start.sh (Linux/macOS) and Start.ps1 (Windows) are the same entry point in each platform's language.

Install & run

Get the server running first, then point an agent at it.

Zero-install AppImage (Linux, easiest)

chmod +x Pi-Scope-1.0.0.AppImage
./Pi-Scope-1.0.0.AppImage
  • Data (SQLite DB + per-run auth token) lives in ~/.pi-scope/ — it survives relaunch and never writes into the read-only AppImage mount.
  • Closing the window stops the server. If one is already listening on the port, the AppImage reuses it instead of starting a second.
  • Build it yourself: ./build-release.sh → apps/scope-desktop/dist/Pi-Scope-<version>.AppImage.

One command (the whole stack)

curl -fsSL https://raw.githubusercontent.com/NerdAtWork24X7/Pi_Scope/main/install.sh | sh
cd Pi_Scope && ./Start.sh                # desktop app (Electron window)

The one-liner downloads the app (no git needed), checks for Node 24+ and installs the dependencies. install.sh --help lists its options (--dir, --ref, --no-deps); running it from a checkout installs that checkout in place. Prefer git: 

git clone https://github.com/NerdAtWork24X7/Pi_Scope.git Pi_Scope && cd Pi_Scope
./Start.sh                               # desktop app (Electron window)

Windows (one command)

irm https://raw.githubusercontent.com/NerdAtWork24X7/Pi_Scope/main/install.ps1 | iex
cd Pi_Scope
.\Start.ps1                              # desktop app (Electron window)

Two conveniences: Start.cmd is the same launcher for a double-click (it bypasses the PowerShell execution policy for that launch only), and install.ps1 can be run as a file when you want to pass arguments (-Dir, -Ref, -NoDeps).

What is Windows-aware (and what is not)

  • The server, Chat, the Office and the Workflow run the same way. A harness on PATH (claude, codex, gemini, …) is a .cmd shim there, which Windows will not run directly — Pi Scope starts those through cmd.exe with every argument escaped, and stops a node by taking its whole process tree down. A Workflow node set to Custom command runs through cmd.exe too, so its variables are %SW_PROMPT%-style instead of $SW_PROMPT.
  • The bundled pi is installed as pi.cmd, and Chat spawns the agent's Node entry directly, so no global pi install is involved.
  • Terminal opens Git Bash when it is installed, otherwise PowerShell (pwsh, then Windows PowerShell) or cmd.exe. The Terminal's live cwd is read from /proc on Linux and lsof on macOS; Windows has neither, so the pane keeps the directory it was opened in and the workspace rail's "follow this directory" injection is skipped.
  • API keys exported from a shell profile (~/.bashrc, ~/.zshrc) are a POSIX-shell convention: on Windows set them on Settings → API keys (or in scope.env).
  • Packaging: build-release.sh builds the Linux AppImage. A Windows package is electron-builder's job — the target is configured in apps/scope-desktop/electron-builder.yml, so run npx electron-builder --win from apps/scope-desktop on Windows, with the server bundle present in apps/scope-desktop/server-bundle.

From the git repo (developers)

git clone https://github.com/NerdAtWork24X7/Pi_Scope.git Pi_Scope && cd Pi_Scope
apps/scope-desktop/run.sh                # requires Node.js 24+

Open the URL it prints (http://127.0.0.1:43190/?token=<uuid>) and you are looking at a live (empty) dashboard. npm run dev adds --watch; the DB defaults to db/scope.db. Override with SCOPE_PORT, SCOPE_HOST, SCOPE_DB_PATH or SCOPE_AUTH_TOKEN.

Launcher flags

Start.sh is the single entry point for every mode — it picks a sane Node (nvm-aware), boots the server and the app together, and on Ctrl-C stops only the server it started. The one exception to "no setup": in desktop mode it runs npm install once, on first run only, to get Electron. The server is started at most once: if one is already healthy on the target port, its token is adopted instead of a second instance being spawned, and a server orphaned by a kill -9 is reaped on the next run. 

./Start.sh                              # desktop app (Electron window, default)
./Start.sh --web                        # headless server + open the WebUI in a browser
./Start.sh --server                     # headless server only, stays in the foreground
./Start.sh --dev                        # server with --watch
./Start.sh --keep-server                # leave the server up after the script exits
./Start.sh --port 8080 --host 0.0.0.0   # override the defaults
./Start.sh --db /path/to/scope.db --token my-token

Start.ps1 is the same, in PowerShell:

.\Start.ps1 -Web                         # headless server + open the WebUI in a browser
.\Start.ps1 -Server                      # headless server only
.\Start.ps1 -Dev                         # server with --watch
.\Start.ps1 -KeepServer                  # leave the server up after the script exits
.\Start.ps1 -Port 8080 -BindHost 0.0.0.0 # override the defaults
.\stop.ps1                               # stop a running server

Per-machine defaults can live in apps/scope-desktop/scope.env (see scope.env.example); real environment variables always win. This matters for the desktop icon, which inherits no shell environment.

Take a test drive (no agent needed)

Want to see it before wiring up an agent? Seed the dashboard with a realistic demo session — a coder adding dark mode, its tester subagent, and a second project with a failed command: 

# server running? then:
node docs/seed-demo.mjs

Instantly populated — click around every view. Re-running is safe (events are idempotent).

Attach a real agent

The dashboard comes alive when a pi agent feeds it. This extension hooks the agent lifecycle and streams telemetry, auto-discovering the server's auth token.

Pi Scope bundles its own pi coding agent. The Chat view, the git-commit-message generator and the in-browser Terminal all launch that bundled copy — with the Pi Scope extension force-loaded — so there is nothing to install and a separate global pi is never used. The bundled agent lives in apps/scope-desktop/pi-bundle (packaged as resources/pi inside the AppImage); point elsewhere with SCOPE_PI_BIN.

The bundled agent also keeps its own agent dir (~/.pi-scope/agent, see SCOPE_AGENT_DIR). Its settings, API keys, model store, sessions and extensions live there, so it never reads or writes your global pi agent dir — the two installations do not interfere, and a pi-scope.ts listed in your global config can't collide with the force-loaded copy.

The steps below are only for a pi you installed yourself and run outside Pi Scope (for example in your own terminal). That agent runs as normal — nothing to learn, no new commands.

One session

pi -e /path/to/Pi_Scope/extension/pi-scope.ts

Every session — add it to your agent config

// your pi agent dir's settings.json
{
  "extensions": [
    "/absolute/path/to/Pi_Scope/extension/pi-scope.ts"
  ]
}

Or copy extension/pi-scope.ts into your pi agent dir's extensions/ folder and list it as "+extensions/pi-scope.ts".

The extension finds the token from tmp/scope_token (dev) or ~/.pi-scope/scope_token (AppImage), so you usually set nothing else. Point it elsewhere with --obs-server-url or OBS_SERVER_URL (default http://127.0.0.1:43190). Full flag and event reference: extension/README.md.

Any tool can feed it

Just POST JSON events to /events:

{ "event_id": "evt-1", "session_id": "sess-1", "seq": 0,
  "ts": "2026-09-07T12:00:00.000Z", "type": "user_message",
  "payload": { "text": "hi agent" } }

Use it from your phone

Pi Scope can bind every interface so a phone on the same Wi-Fi can open the Chat view live, alongside the desktop.

1. Bind to the LAN

cp apps/scope-desktop/scope.env.example apps/scope-desktop/scope.env
# then uncomment:  SCOPE_HOST=0.0.0.0

scope.env is read at launch, so this works from the desktop icon too. Real environment variables still win, so SCOPE_HOST=0.0.0.0 ./run.sh overrides the file. Running from source instead of the launcher? SCOPE_HOST=0.0.0.0 npm start in apps/scope-server works the same way, and the boot banner prints the phone URL.

2. Scan the QR

Start Pi Scope and click the phone icon in the header. A QR appears — point your phone's camera at it and Pi Scope opens in a mobile layout, not a shrunk copy of the desktop screen. The QR already carries this run's auth token, so bookmark it rather than sharing it. If the machine has more than one network interface (Wi-Fi, ethernet, docker), pick the address the phone can actually reach.

What the mobile layout is

  • A ☰ drawer of workspaces and sessions, with their live / waiting / stopped state.
  • The selected session's transcript — recorded messages plus the live stream as pi works.
  • A composer that sends prompts straight to pi; a question pi asks appears as an answerable card, and Stop aborts the run.
  • New session (the ＋ in the header) opens a sheet to pick the workspace, model, agent team and mode; the first message spawns pi with exactly those settings.
  • A ✕ on each drawer row deletes that session, killing the pi subprocess behind it first. It asks for confirmation — the delete cannot be undone.
  • The desktop views (Terminal, Files, Git, Checkpoints, Office) are deliberately absent, and the phone does not download them: it loads mobile.html + mobile.js + mobile.css, not the desktop bundle.

The layout is chosen at the document, three ways:

How you open itWhat you get
/m?token=… (the QR)The mobile layout, always
/?token=… on a phoneThe mobile layout (User-Agent / Client Hint)
/?token=…&ui=desktopThe desktop UI, even on a phone

The 🖥 button in the mobile header opens the same session in the desktop layout; ui=mobile does the reverse, so neither is a one-way door.

This exposes a shell. With SCOPE_HOST=0.0.0.0 anyone on that network who knows the token can drive your agents. The mobile layout is smaller than the desktop UI, not harmless: prompts run real commands on this host, it can retarget a project's team/mode, and it can delete sessions — and the desktop layout (reachable with ui=desktop) adds Terminal, a real shell, plus file edits and git operations. Only do this on a network you trust. The token is minted randomly at boot; pin SCOPE_AUTH_TOKEN in scope.env if you want a stable URL.

Chat-spawned pi subprocesses also get the workspace venv bin dirs prepended to PATH, and PLAYWRIGHT_BROWSERS_PATH restored from the user's shell rc files (or Playwright's default cache dirs) when the server env lacks it — so web-fetch finds its Chromium browser even when the server was launched from a GUI session that never sourced the shell rc.

The full HTTP API — all endpoints, auth rules and the SSE stream — is documented in apps/scope-server/README.md.

Tips & FAQ

  • UI state lives in the URL hash — view, filters and selected session are all saved there, so you can bookmark or share a view. The auth token stays in the ?token= query string, never the hash.
  • Sessions auto-refresh (every 10s) and stream live over SSE — new agents and events appear without reloading. The top-bar dot turns green when the feed is connected.
  • The terminal is shared state. The Files, Checkpoints and Git panes follow the terminal's working directory — or set it manually in the Terminal pane's cwd box.
  • One rail, every view. The Workspaces rail on the left is the same component in every view: pick a workspace and it becomes the shared working directory, fold subagent groups open or closed, open a session straight into Single or Trajectory, or delete it from the rail.
  • Where's my data? A single SQLite file (db/scope.db in dev, or ~/.pi-scope/ packaged), chmod 0600. Delete sessions from the sidebar — or DELETE /sessions for everything.
  • What's captured? Session start/end, every user/assistant message, thinking blocks, tool calls + results (with exit codes), LLM request args + system prompt, model changes, compactions and branch navigation.

For AI agents & contributors

This repository is structured so an AI coding agent can onboard quickly. The server API, environment variables and full endpoint list live in apps/scope-server/README.md; the telemetry extension and its flags are documented in extension/README.md.

Every feature is a plugin, so the fastest way to change Pi Scope's behaviour is usually to write one rather than edit the core. Start with apps/scope-server/plugins/README.md — it covers manifests, the api.route / api.onEvent / api.store / api.log API, client bundles and where state is persisted — and copy the working example in examples/plugins/hello-insights/.

  • Demo data: docs/seed-demo.mjs — the script that created the screenshots on the showcase page.
  • UI: vanilla JS, zero frameworks — apps/scope-server/public/. Views are plugins: plugins.js is the client host/registry, plugins-builtin.js registers the shipped views, and app.js setView() is registry-driven — it knows no view by name. Office is the standalone one: its client bundle, stylesheet and server module all live in apps/scope-server/plugins/office/, loaded from its manifest like any third-party plugin's.
  • Plugins: apps/scope-server/plugins.ts is the server host (discovery, enable/disable, route gating, event hooks, per-plugin storage); apps/scope-server/plugins/ holds the built-in feature manifests.
  • Server: single-file Node HTTP + SSE + SQLite — apps/scope-server/server.ts.
  • This site: docs/ — plain HTML/CSS/JS, no build step, no CDN. It is published with GitHub Pages.
